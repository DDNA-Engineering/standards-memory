# Contributing to StandardsForge

StandardsForge accepts focused contributions that strengthen exact evidence, deterministic behavior, secure local operation, and practical defense-engineering workflows.

Start with the [wiki](docs/wiki/README.md), [product baseline](docs/PRD.md), [architecture](docs/ARCHITECTURE.md), relevant [decision record](docs/adr/README.md), and selected task in [backlog/tasks.json](backlog/tasks.json).

## Non-negotiable boundaries

Every contribution must preserve:

- exact source, edition, representation, package, and citation identities;
- separation between source evidence, derivation, automated checks, and human approval;
- explicit uncertainty, unsupported regions, and incomplete coverage;
- trusted local policy as the authorization source;
- read-only, offline query behavior with no hidden network or model fallback;
- applicability, tailoring, compliance, baseline selection, and approval as human-owned decisions.

Do not submit proprietary standards text, private customer data, credentials, classified information, CUI, ITAR-controlled data, or other restricted material. Use synthetic fixtures or content with demonstrable redistribution permission.

## Choose a bounded contribution

Work one vertical slice at a time. A good slice includes:

1. one explicit requirement or defect;
2. the smallest contract and implementation change needed;
3. positive behavior;
4. negative and tamper cases;
5. migration or compatibility handling when stored data changes;
6. documentation of the observed result and remaining limits.

Avoid mixing refactors, formatting, generated artifacts, corpus refreshes, and product behavior in one pull request unless they are inseparable.

## Development setup

Windows PowerShell:

```powershell
py -3 -m venv .venv
$Python = Join-Path $PWD '.venv\Scripts\python.exe'
& $Python -m pip install --upgrade pip
& $Python -m pip install -e '.[mcp,compiler,contract]'
& $Python -m pip check
$env:PYTHONPATH = Join-Path $PWD 'src'
```

Use the repository virtual environment rather than an unrelated system or Anaconda interpreter.

## Where changes belong

| Change | Update together |
|---|---|
| Query or response semantics | Library, CLI, MCP, operation contracts, examples, negative cases, and model guidance |
| Pack or annotation semantics | Schema, validator, compiler, migration/compatibility behavior, fixtures, and tamper tests |
| Storage behavior | Schema version, migration, rollback notes, integrity tests, and cache invalidation |
| Acquisition or compilation | Manifest/report contracts, parser boundaries, restart behavior, failure accounting, and provenance |
| Release artifact | Builder, closed inventory, provenance, clean-extract acceptance, checksum, and release documentation |
| Documentation only | Root quickstart or wiki page, links, commands, evidence boundary, and dated claims |

Generated artifacts must be regenerated by their declared tool. Do not hand-edit generated contracts, inventories, receipts, or provenance to make a check pass.

## Required validation

Run the focused tests for the changed slice first. Before opening a normal pull request, run:

```powershell
$env:PYTHONPATH = Join-Path $PWD 'src'
python -m pip check
python scripts/validate_contracts.py
python -m unittest discover -s tests -v
python scripts/run_benchmark.py benchmarks/synthetic-contract-v1.json
python -m compileall -q src tests scripts
git diff --check
```

Documentation-only changes may use a proportionate gate: validate every changed local link and heading anchor, run documented commands when they changed, and run `git diff --check`. State clearly when the code suite was not run because runtime behavior did not change.

Changes that affect packaging, installation, dependencies, starter behavior, or release evidence must also run:

```powershell
python -m pip download --disable-pip-version-check --no-deps --only-binary=:all: `
  --dest build/toolchain-cache setuptools==84.0.0

python scripts/validate_installed_wheel.py `
  --build-tool-dir build/toolchain-cache `
  --output-dir build/ci-wheel

python scripts/build_starter_distribution.py `
  --wheel-dir build/ci-wheel `
  --output build/standardsforge-starter.zip

python scripts/validate_starter_distribution.py `
  build/standardsforge-starter.zip
```

Prepared-corpus changes require the additional clean-extract acceptance in the [validation and release guide](docs/wiki/VALIDATION_AND_RELEASES.md).

## Fixtures and source material

- Prefer small synthetic fixtures that isolate one behavior.
- Record exact fixture identities and digests when the test depends on bytes.
- Keep acquired PDFs, generated packs, databases, and object stores in ignored local paths.
- Never make a rights claim authorize installation or query access.
- Do not scrape sources whose terms prohibit automated acquisition or processing.
- Treat PDF text as untrusted input and preserve parser failure as failure.

## Contracts and compatibility

Machine contracts are closed and versioned. When semantics change:

1. update the schema and executable examples;
2. add malformed and adversarial negatives;
3. update the requirement mapping and selected backlog task;
4. preserve old readers or add an explicit migration;
5. never invent semantic classification, review, applicability, or approval during migration.

See [contract versioning](contracts/SCHEMA_VERSIONING.md) and the [contract index](contracts/README.md).

## Documentation

Keep the root [README](README.md) focused on starting the prepared offline library. Put deeper workflows and explanations in the [wiki](docs/wiki/README.md).

Documentation must identify:

- whether a command runs from a prepared distribution or source checkout;
- whether evidence is local, CI-observed, published, or user-accepted;
- the artifact version, snapshot date, or commit for time-sensitive claims;
- the difference between prepared end-user setup and maintainer acquisition/compilation;
- any unmeasured or unsupported behavior.

## Commit and pull-request standard

Sign every commit using the Developer Certificate of Origin convention:

```powershell
git commit -s
```

The repository pull-request template prompts for the required evidence. A pull request should include:

- the requirement, task, or defect addressed;
- the user-visible and machine-contract change;
- exact commands run and observed results;
- positive, negative, tamper, and compatibility coverage;
- fixture or artifact digests when relevant;
- security, authorization, and rights impact;
- migration and rollback impact;
- known limits and work intentionally left out.

Do not claim deployment, publication, protected CI, signed provenance, or end-user acceptance from local tests.

## Security reports

Report suspected vulnerabilities through GitHub's private vulnerability reporting flow described in [SECURITY.md](SECURITY.md). Do not disclose them in a public issue, discussion, pull request, fixture, or pack.
