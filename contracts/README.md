# Machine contracts

Contract lifecycle rules and the schema change log are in [SCHEMA_VERSIONING.md](SCHEMA_VERSIONING.md). Every generated artifact family must have an exact schema-validation test in addition to runtime validation of file, digest, authorization, and cross-document invariants.

The JSON Schemas describe the public 0.1.0 pack manifest, inventory, records, rights claims, and trusted local policy shapes. Runtime validation is deliberately stricter where filesystem evidence is required: it verifies inventory closure, byte counts, SHA-256 values, source quote presence, edition consistency, dependency targets, and data-only paths.

`source-catalog.schema.json` describes tracked metadata for locally acquired official sources. Runtime validation additionally enforces stable DLA Quick Search URLs, safe PDF filenames, directory closure, PDF signatures, exact byte counts, and SHA-256 digests. The catalog is not a download script and its rights metadata does not authorize repository redistribution.

`corpus-extraction-report.schema.json` separately closes the DLA corpus compiler's multi-component report, including composition identity, aggregate counts, exact compiler and parser-limit policy, component source identities, encryption status, and every physical-page extraction outcome. It is intentionally not accepted by the single-PDF report schema.

`extraction-report.schema.json` describes deterministic PDF text-layer compilation results and records the exact isolated-worker protocol and fixed limit policy. Compiled PDF records cite the original inventoried PDF and an exact half-open UTF-8 range in a separate inventoried text sidecar. `records-v0.2.schema.json` removes the duplicate page-text field from portable page records; validation reconstructs the exact in-memory text from that verified byte range. The 0.1 records contract remains supported for existing and structural packs. The report keeps text extraction, OCR, visual fidelity, tables, figures, clause boundaries, and obligation classification as independent dimensions.

`pdf-worker-request.schema.json` and `pdf-worker-result.schema.json` close the private parser-process protocol. A request binds exact source bytes, expected pages, dependency versions, extraction and encryption modes, normalization, and every positive resource/output limit without carrying an output path in its digest. A result inventories one normalized UTF-8 regular file per physical page, consecutive ordinals, content-stream sizes, bytes, and hashes, with `result.json` activated last. Runtime validation rejects links, junctions, extra or missing files, malformed UTF-8, digest/count/order drift, and any partial result.

`structure-annotations.schema.json` describes edition-bound agent or human review over ordered exact physical-page UTF-8 spans. Version 0.2 may attach `semantic-record.schema.json` decompositions and requires complete reviewer method/tool provenance. `review-event.schema.json` binds the emitted review event to the exact record content while explicitly denying any project-applicability or approval decision. `records.schema.json` carries stable logical IDs, content hashes, optional semantics and review, parent relationships, typed targets, and relationship evidence spans separately from physical locations.

Pack manifests distinguish `page_text`, `derived_structure`, `reviewed_structure`, and `curated_records`. `derived_structure` is an automated, unreviewed representation: it may expose navigation candidates and unsupported regions but cannot imply semantic correctness, confirmed obligations, or human approval.

`query-operations.json` identifies the six read operations and their authority/pinning invariants. `mcp-tools.json` fixes the local stdio MCP surface, trusted startup-principal boundary, and exact caller-visible arguments. Returned packet details remain pre-release and are locked by the acceptance tests; no HTTP adapter is implemented.

`query-response.schema.json` defines operation-specific detailed result packets for all six reads, including first and final obligation-enumeration pages. Contract 0.2 also defines the versioned edition-diff packet: exact record IDs remain authoritative, logical-key matches are review-required candidates only, source-only moves are explicit, and required-dependency impact paths identify the independently traversed before or after graph. `success-response.schema.json` wraps detailed, compact, and concise results in the shared successful transport envelope; `error-response.schema.json` defines the typed failure envelope. The contract gate checks every schema against its declared metaschema, validates concrete repository documents, and exercises actual service responses plus malformed negative cases.

`distribution-scope.schema.json` defines the qualified source baseline shipped with a prepared distribution. It binds the release to the exact bundled acquisition manifest and records its selection, exclusions, build outcomes, extraction gaps, representation-specific review state, and limits without turning publisher currentness into project approval.

`prepared-distribution.schema.json` defines the final bundle manifest, including its exact file inventory, fixed archive epoch, pinned wheel builder identity, wheel digest, hash-bound offline MCP wheelhouse, corpus compiler version, installed package counts, and source-baseline identity.

`wheel-build-provenance.schema.json` records the exact source-file inventory, separates files copied into the wheel build from release-only dependency metadata, binds the exact build-tool lock and backend artifact, fixes the source epoch, records observed builder Python and pip versions, denies authentication, and binds the two-build result to the wheel handed to distribution builders.

`cyclonedx-release-sbom.schema.json` is the closed StandardsForge profile of CycloneDX 1.7 used for the dependency-free core wheel and synthetic starter. It requires an explicit root dependency node so omission cannot be mistaken for zero dependencies. `release-build-statement.schema.json` closes the unsigned in-toto Statement v1 and SLSA provenance v1 shape while requiring the local builder, source-control state, and no-authentication claim. `release-evidence.schema.json` binds the exact subjects, four deterministic sidecars, source inventory, dependency and build-tool locks, protected workflow verification policy, and explicit unsigned status. Runtime verification recomputes every available digest and cross-link without fetching URLs; signed producer identity is verified separately against the CI attestation bundle and trusted roots.

`starter-bundle.schema.json` defines the closed cross-platform synthetic starter manifest: fixed archive construction, exact verified wheel and provenance, two fictional pack identities, trusted policy, local state paths, setup and launcher entry points, readiness and evidence smokes, and explicit false real-corpus claims. `starter-receipt.schema.json` binds a completed local installation to that manifest, wheel, provenance, policy, package digests, state paths, full-integrity doctor result, and discovery/context smokes. Runtime validation remains stricter: it rejects extra, missing, unsafe, duplicate, case-colliding, linked, or changed files before setup writes and rechecks bundle plus receipt on every rerun.

`handoff-candidate.schema.json` closes the caller-authored requirement or test-basis candidate, including author type, method, timestamp, mandatory agent tool/configuration provenance, bounded assumptions and unresolved questions, and proposed-but-not-approved tailoring. `engineering-handoff.schema.json` binds that draft to one exact detailed get-clause packet, immutable package and root identities, a canonical local locator, packet and draft digests, rights provenance with no authorization effect, full source basis, fixed host-owned decision states, and the static reader trust boundary. `handoff-bundle.schema.json` closes the deterministic directory manifest over the JSON handoff and no-script HTML reader. These artifacts transfer evidence, not access authority, applicability, compliance, tailoring approval, baseline selection, or engineering approval.

`benchmark-suite.schema.json` defines a reviewed, content-bound synthetic qualification suite over exact local package identities, cases, expected evidence, critical and forbidden facts, completeness checks, and zero-tolerance release gates. `benchmark-run.schema.json` preserves every cold and immediate-warm response, its canonical byte count and digest, exact assertion numerators and denominators, source and runner identity, and explicit unmeasured dimensions. Runtime validation recomputes the suite, sample, run, summary, metric, and case-set relationships that JSON Schema cannot express. These contracts do not permit a synthetic suite to claim real-document quality.

`doctor-response.schema.json` closes the portable readiness report. It distinguishes quick selected-package integrity from full installed-package integrity, preserves every required or advisory check and summary count, records the exact query-smoke selector and verification outcome, and fixes the read-only and no-network boundary. A ready report proves only the named local runtime, store, policy scope, package evidence, and exact read path; it is not an applicability, compliance, approval, semantic-completeness, or MCP-host-configuration claim.

The MCP contract also records the client-visible MIL-STD reading guidance and exact per-tool descriptions. Initialization guidance covers edition/representation selection, immutable package pins, discovery versus evidence, governing context, tailoring and applicability, and honest classification coverage. This guidance does not expand the six-tool read-only surface or grant authority.

`compact-evidence-response.schema.json` describes the opt-in `compact_evidence_v1` response profile for `get_clause` and `build_context`. Omitting `response_profile` retains the established detailed JSON response. Compact records keep exact text and canonical record IDs while packet-local references navigate deduplicated source and derivation dictionaries; byte budgets cover the complete compact JSON packet.

`concise-evidence-response.schema.json` describes the measured `concise_evidence_v1` profile. It collapses verified check dictionaries, interns structural spans and provenance, and merges duplicate governing-edge declarations while retaining exact text, canonical IDs, citations, coverage, authorization, and unresolved relationship meaning.

Search may be constrained by an authorized package digest and exact/dot-descendant clause prefix. Contract version 0.2 exposes `exact_phrase`, `all_terms`, and `any_terms`; omission preserves `all_terms`. Queries over 32 parsed lexical chunks are rejected, and every response exposes the mode, normalized query, and parsed chunks together with source citations, indexed-text snippets, and available structural ancestry. Search operators are never accepted as raw syntax. These are narrowing and discovery controls only; query execution has no synonym, network, model, or scope-broadening fallback.

`get_clause` accepts `clause_reference`, canonical `record_id`, or both. At least one selector is required; when both are supplied they must identify the same record in the pinned package. This makes the complete `evidence_selector` returned by search directly replayable without discarding canonical identity.
